# Generation

## What this is for

`model.generate(prompt, max_new_tokens=N)` runs one forward for the prompt and
one per new token, and every standard value is served once per forward. So
`layer_output` on the prompt call is `[batch, prompt_len, hidden]` and on a
decode step `[batch, 1, hidden]`; `next_token_probs` is the distribution that
produced each step's token; and `input_ids` is the one token the step is fed.
`tracer.iter[...]` binds a stretch of the block to chosen steps, and
`tracer.result` is the generated ids. How `generate` and `tracer.iter` work is
nnsight's: nnsight docs/usage/generate.md and docs/usage/iter-all-next.md.
This page is what nnter's values look like under them.

## Canonical pattern

```python
from nnter import StandardizedTransformer

model = StandardizedTransformer("openai-community/gpt2")

resid, probs = [], []                                  # made outside the block: a name bound inside does not survive it
with model.generate("The Eiffel Tower is in the city of", max_new_tokens=3, do_sample=False) as tracer:
    for step in tracer.iter[:3]:                       # steps 0, 1, 2
        resid.append(model.layers[6].layer_output.save())
        probs.append(model.next_token_probs.save())    # [batch, vocab], the distribution this step samples from
    ids = tracer.result.save()                         # [batch, prompt_len + 3]

[r.shape for r in resid]    # [batch, prompt_len, 768], then [batch, 1, 768] twice
probs[0].argmax(-1) == ids[:, -3]                      # greedy: each step's argmax is the token it appended
```

The lists are made before the `with`: a name bound inside the block does not
survive it unless it is `.save()`d, and a list built inside is such a name.

## One value per forward call

Every value on the root and on the blocks answers for the current call:

| value | prompt call (step 0) | decode step |
| --- | --- | --- |
| `model.input_ids`, `model.input_size` | `[batch, prompt_len]` | `[batch, 1]`: the token generated by the previous step |
| `layers[i].layer_output`, `self_attn.attention_output`, `mlp.mlp_output`, `token_embeddings` | `[batch, prompt_len, hidden]` | `[batch, 1, hidden]` |
| `self_attn.attention_queries`, `attention_head_outputs` | `seq == prompt_len` | `seq == 1` |
| `self_attn.attention_keys`, `attention_values` | `[batch, kv_heads, prompt_len, head_dim]` | `[batch, kv_heads, prompt_len + step, head_dim]`: the cache |
| `self_attn.attention_scores`, `attention_probabilities` | `[batch, heads, prompt_len, prompt_len]` | `[batch, heads, 1, prompt_len + step]` |
| `mlp.router_logits` (a mixture of experts) | `[batch, prompt_len, experts]` | `[batch, 1, experts]` |
| `mlp.expert_weights`, `expert_indices` | `[batch, prompt_len, top_k]` | `[batch, 1, top_k]` |
| `mlp.expert_outputs` | `[batch, prompt_len, top_k, hidden]` | `[batch, 1, top_k, hidden]` |
| `mlp.routed_output`, `shared_expert_output` | `[batch, prompt_len, hidden]` | `[batch, 1, hidden]` |
| `model.logits` | `[batch, prompt_len, vocab]` | `[batch, 1, vocab]` |
| `model.next_token_probs` | `[batch, vocab]` | `[batch, vocab]` |

On a decode step the pattern has one query row over every cached key, so
`attention_probabilities[0, h, 0]` is what head `h` of the new token attends
to across the whole context so far ([attention-interior.md](attention-interior.md)).

## Picking steps

`for step in tracer.iter[k]` binds the body to step `k`; `tracer.iter[:n]` to
the first `n` steps; `tracer.iter[1:]` to every decode step. A read outside
any loop binds to step 0, the prompt call.

```python
with model.generate(prompt, max_new_tokens=3, do_sample=False) as tracer:
    for step in tracer.iter[1]:
        one = model.layers[6].layer_output.save()      # [batch, 1, hidden]: the first decode step
    ids = tracer.result.save()
```

A write at a step reaches that step and everything after it. Zeroing a
block's output on step 1 leaves the prompt's token and step 0's token alone
and changes the rest:

```python
with model.generate(prompt, max_new_tokens=3, do_sample=False) as tracer:
    for step in tracer.iter[1]:
        model.layers[6].layer_output[:] = 0
    ids = tracer.result.save()
```

## Read order within a step

Inside one step's body the reads follow the forward like in a trace:
`input_ids` first, a block's `self_attn.*` and `mlp.*` before that block's
`layer_output`, `logits` and `next_token_probs` last, and a block's interior values
before its `attention_output`.

A misplaced read fails differently here. In a single trace it raises
`OutOfOrderError`. Inside `tracer.iter` under `generate` it usually does not: the read
waits for the value's *next* occurrence, which is the next step's, so the list is
shifted by one step without an error. On GPT-2, reading block 6's
`attention_probabilities` after its `attention_output` in `tracer.iter[:3]` returns steps
1 and 2's patterns as entries 0 and 1, and the read on the last step is never reached,
which ends the loop with nnsight's `was never reached: the loop asked for a step the run
did not make` warning. That warning blames the loop bound; the cause is the order. Check
the shapes against the step (a decode step's pattern is `[batch, heads, 1, prompt + step]`)
and treat that warning as a read-order error.

## Gotchas

- **`tracer.result` after an open loop is never bound.** `tracer.iter[:]` and
  `tracer.all()` end by outrunning the run, and the statements after the loop
  do not execute (nnsight warns, and does not raise). Use a bounded
  `tracer.iter[:N]` with `N == max_new_tokens`, and `min_new_tokens=N` when an
  EOS could stop the run early, or put `tracer.result` in a loop of its own.
- **Decoding follows the checkpoint's `generation_config`.** Pass
  `do_sample=False` for a deterministic run; many instruct checkpoints ship
  `do_sample=True`.
- **`next_token_probs` is the last position of the current call.** On a decode
  step that is the one token; on the prompt call it is each row's last token,
  which is each prompt's own last token only under left padding.
- **The keys and values grow with the cache; the queries do not.** A head-wise
  edit of `attention_keys` on a decode step touches the whole context.
- **On a DeltaNet hybrid, a decode step runs the recurrent kernel**, and
  `linear_attn.state_input` carries the previous step's `state_output`; see
  [delta-net.md](delta-net.md).
- **On Mamba-1 and Mamba-2, a decode step reads `state_output` before
  `attention_head_outputs`** (on Mamba-1 the reverse of a prompt's scan); the wrong order returns the next
  step's state or cuts the loop short ([selective-scan.md](selective-scan.md#gotchas),
  [state-space.md](state-space.md#gotchas)).
